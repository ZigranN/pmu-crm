# Шаг 3.4d — подтверждённые условия предложения

Дата: 18.09.2026. Основание: Master Specification §§9–10,44.

## Реализовано

- `src/features/commercial-terms/`: Owner/Admin command `cycle.terms-confirm.v1`, отдельная read-модель и панель сделки. `OFFER_MANAGE` разрешает подтверждение; `PAYMENT_READ` и текущий resource scope разрешают чтение, включая назначенного Master. AI доступа не получает.
- Одна зона: live catalog/master price version, fixed amount с сервера; для estimate/range/quote требуется явная человеческая сумма. Multi-zone Custom Offer: ссылка на item последней редакции того же клиента/студии/зоны/мастера; `amountCents=NULL`, общая сумма предложения только как подписанный справочный snapshot. Распределение денег не имитируется.
- `cycle_commercial_terms`, migration `0020_cycle_commercial_terms.sql`: append-only редакции, actor/reason, source snapshot, confirmedAt, reviewAt, command receipt. Защита от изменения/удаления и несоответствия receipt/offer item на уровне БД.
- Дата пересмотра задаётся человеком. Ориентир «неделя» не заменяет явного решения. UI показывает время студии, ввод подписан как время устройства. На точной границе срока возникает признак human review; сумма, запись, задача контакта и стадия не меняются.
- Продление/замена — новая редакция с актуальной ценой и причиной. Проверяются версия цикла и коммерческой истории; конкурентное устаревшее подтверждение отклоняется. Повтор после потери ответа возвращает прежнюю редакцию.
- Thinking follow-up rescheduling не продлевает условия. История после изменения каталога/мастера сохраняется. Проведённая процедура, связанный процедурный визит или оплата блокируют подтверждение новых условий этим ранним процессом.
- Запись условий, audit и receipt атомарны. Внешних эффектов у команды нет, поэтому отдельный outbox job не создаётся.

Результаты итогового CI фиксируются в PR после выполнения проверок. Миграция проверяется только на disposable БД. Neon не изменялся.

## Границы готовности

Это реализация ранних коммерческих условий, а не ledger или полный PMU acceptance. Phase 5/6 должны использовать latest immutable terms по cycleId и перепроверять live cycle/source/reviewAt перед booking/финансовой операцией; legacy `commercialSnapshot` не объявляется вторым источником истины. `offerRevisionId` старой оболочки цикла не заполняется параллельно — точная связь хранится через offerItemId новой редакции.

Total Face, финансовая коррекция после операций, автоматический outbound, фоновые напоминания о пересмотре, применение условий при booking/ledger остаются в соответствующих будущих фазах. Просрочка сейчас отображается при чтении панели; автоматическое подтверждение отсутствует. Полная история хранится, UI ограничен 50 последними редакциями. Самостоятельное продление после изменения цены требует новой human approval; старые snapshots не пересчитываются.
